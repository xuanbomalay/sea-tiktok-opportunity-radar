# 从项目到可解释的求职作品

本项目研究马来西亚、泰国、越南三个市场的商品搜索样本。它的目标是把数据采集、SQL 分析、时间序列验证、可视化和 Agent 工程连成可复现流程。

## 先看哪里

1. 打开正式看板，确认是否已取得真实数据、观察日期和各国状态。
2. 打开带橙色提示的 **synthetic demo**，了解有历史后图表和模型评估的样子。演示商品和数字由程序生成，不能用于市场结论。
3. 阅读 `radar/parsing.py`：理解为什么 `1K+` 不能当成精确的 1,000 单。
4. 阅读 `radar/analysis.py`：理解同一商品、同一来源、同一日期跨度的比较，以及样本变化造成的偏差。
5. 阅读 `radar/modeling.py`：理解为什么七天标签必须在训练截止时间前成熟。
6. 阅读 `radar/agent.py`：模型只能查询已有指标、比较市场、选择证据，发布的数字由代码渲染。

## 工具如何分工

本地 Python 用于开发、调试和复现；GitHub Actions 每天在云端运行；GitHub Pages 展示静态网页；Colab 提供阅读和研究入口。电脑关机不影响已配置的云端任务。

Apify 是数据获取接口。API、BeautifulSoup、浏览器自动化都是获取方式，技术价值取决于字段质量、稳定性、成本控制与研究验证。本项目不为了展示技术而增加无必要的采集手段。

DuckDB 用于分析查询，Parquet 用于列式导出，SQLite 用于预算和去重账本。这三个组件承担不同工作。原始结果及账本只留在私有数据仓库。

## 图表怎么看

- 气泡图：横轴是样本卖家数/商品数，纵轴是同商品面板的七天增量增长率。没有历史就没有点，不补假数据。
- 热力图：显示实际采到了多少商品，不表示市场规模。
- 趋势图：默认展示搜索样本中位数，样本构成变化也会改变曲线；选定单一国家后才能查看本币价格。
- 候选表：是下一步研究清单，不是“保证能卖”的商品推荐。
- 模型评估：预测未来七天公开售出计数的增量，不等同于真实订单或收入。实际表现弱于简单基线时也保留结果。

## 可以在面试中讲什么

重点讲清业务问题、样本偏差、特征可用时间、标签成熟时间、基线、失败实验、成本预算、断点恢复和可追溯证据。先说明研究限制，再用实际运行日志支持完成的能力。

尚未实测的“效率 4 倍”、尚未发生的品牌孵化或销售闭环，不能作为这个代码项目的既有成果。项目提供计时模板，等十组人工/自动同质量任务有完整记录后再计算。
